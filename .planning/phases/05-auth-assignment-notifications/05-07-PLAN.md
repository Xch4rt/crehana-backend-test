<objective>
The three auth use cases and the DTOs they speak: registration, login that cannot be used to
enumerate accounts, and the token-to-user resolution the actor seam will call on every request.

Purpose: this is where AUTH-01, AUTH-02, AUTH-04 and AUTH-05 become behaviour rather than adapters.
Every one of them is testable with no HTTP and no database, against the fakes, which is what makes
D-12's indistinguishability a property with a test rather than a claim in a document.
Output: `RegisterUser`, `Login`, `AuthenticateActor`, `GetProfile`, and their commands and results.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated body → account creation | `POST /auth/register` is open by definition, so everything it accepts is attacker-controlled |
| unauthenticated credentials → the user table | The login lookup is the classic enumeration surface |
| bearer token → an identity every other use case trusts | `AuthenticateActor`'s result is the `actor_id` the whole authorization model is built on |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-5-05 | Information disclosure | user enumeration through login | mitigate | One refusal constructed in one place for both legs, asserted equal on class, code, message and details; the unknown-email leg calls `dummy_verify`, asserted by call count rather than by timing |
| T-5-06 | Information disclosure | user enumeration through register's 409 | **accept** (D-23) | AUTH-01 mandates the 409, which is an oracle by construction.
