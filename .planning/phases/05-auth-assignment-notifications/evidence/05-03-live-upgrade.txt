05-03: revision 0002 applied to a POPULATED database

The integration suite proves 0002 against taskmanager_test, which
migrated_database empties (downgrade base) before every session - so the
suite never exercises the one case the transient server_default exists for:
a NOT NULL column arriving in a table that already holds rows. The compose
database does hold one, the Phase 4 demo-seed account, and it was still at
0001. This is that run, through the container's own entrypoint
(docker/entrypoint.sh -> alembic upgrade head), not through a hand-typed
statement. Nothing was dropped and no volume was removed.

=== THE BUG THIS RUN FOUND, AND ITS FIX ===

The first restart after the upgrade did NOT reach healthy. Step 2b of
docker/entrypoint.sh - the Phase 4 demo seed - names its columns by hand,
and full_name was not among them:

  sqlalchemy.exc.IntegrityError: (psycopg.errors.NotNullViolation) null
  value in column "full_name" of relation "users" violates not-null
  constraint
  DETAIL:  Failing row contains (00000000-0000-4000-8000-00000000de00,
  demo@taskmanager.local, !, 2026-09-19 15:18:04.798065+00,
  2026-09-19 15:18:04.798065+00, null).

ON CONFLICT DO NOTHING did not absorb it, and could not have: PostgreSQL
checks NOT NULL while building the candidate row, before the arbiter index is
consulted, so the clause never runs. The container aborted under set -eu and
docker compose up was broken - the project's core value, in one column.

No test in the suite could have caught this. The suite migrates
taskmanager_test and never runs the entrypoint, and the entrypoint is a
heredoc rather than a module under src/taskmanager (ADR-037), so nothing
imports its INSERT. This is the cold-start rehearsal doing the job ADR-037
says it is there for.
