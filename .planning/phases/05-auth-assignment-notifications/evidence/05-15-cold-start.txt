Plan 05-15 Task 2 - the cold-start rehearsal on an empty volume
===============================================================

ATTEMPTS: ONE. The sequence below ran start to finish on the first attempt. No
step failed, nothing was fixed and re-run, and nothing is stitched together from
two runs - which matters, because a cold start assembled from two attempts is
not a cold start.

Captured 2026-09-19 on macOS (Darwin 25.5.0) / Docker Desktop, linux/arm64,
against the committed docker-compose.yml, Dockerfile, docker/entrypoint.sh and
Makefile, with no override file of any kind and no edit to any of them - the
last command in this transcript is `git status --porcelain`, and it prints
nothing.

This extends evidence/03-10-cold-start.txt and evidence/04-11-cold-start.txt
rather than replacing either. Phase 3's rehearsal showed that a fresh stack
reaches `api healthy`; Phase 4's walked the mandatory use case on it. Neither
could show this phase's path, because both ran against a container that seeded
a demo account at boot. Plan 05-10 deleted that step (D-14), so the stack now
starts with **zero** users and the documented path begins with a registration -
and the first person to run that path must not be the evaluator.

What this transcript proves, in order:

  1. STEP 0 records what the wipe was about to destroy, so "the volume was
     empty afterwards" is a change rather than an assertion about an unknown
     starting point. The compose `taskmanager` database held exactly one user,
     one task list and one task - leftovers of the Phase 4 rehearsal and of the
     account plan 05-10 stopped writing - plus the throwaway `taskmanager_test`
     database. That row is the ONLY place a demo account appears in this file,
     and it appears as something being deleted.
  2. `docker compose down -v` removes the two containers, the `test_default`
     network and the `test_pgdata` volume, and nothing else: no image, and no
     container of the profiled `test` service (03-10's finding - `down -v` does
     not reach a disabled profile; none was running here). `docker volume ls`
     afterwards prints the header and no row.
  3. `docker compose up -d --build`. The `--build` flag is what an evaluator
     gets for free and this machine did not: `down -v` discards containers,
     network and volume but NOT images, and the `test-api` image on this
     machine predated plans 05-11 and 05-12 - it carried no `configure_logging()`
     in `create_app()` and none of the four routes this phase added. Somebody
     cloning the repository has no image at all, so their plain
     `docker compose up` builds one; `--build` is the faithful equivalent here.
     The build output is verbatim below: two layers re-ran (`COPY src` and
     `pip install --no-deps .`), the rest came from cache.
  4. `api` reaches `healthy` 7 seconds after `up` returns - three polls, 2s
     apart - and `db` with it. `docker compose ps -a` shows two services, not
     three: `test` stays out of `up` because of its profile.
  5. The startup log shows **three** steps and no fourth. The readiness probe
     is silent on success (a ready database prints nothing, by design), then
     Alembic runs `-> 0001, baseline` and `0001 -> 0002, full_name and the
     assignee index`, then uvicorn starts. There is no seed line, and
     `SELECT count(*) FROM users` on the fresh volume returns **0**: T-5-03's
     mitigation - the project ships no credential - observed rather than
     claimed.
  6. The documented path, and it is the *shipped* documentation rather than a
     path invented for this file: `/openapi.json`'s own description is printed
     first, and what follows is those three numbered steps. Register, register
     a second person, log in, read the profile back, create a list, create a
     task in it, `GET /api/v1/users` to discover the second person's id, and
     `PUT .../assignee` naming it. Every request and every response is here,
     headers included.
  7. The invitation (NOTF-02, D-15, D-24). One command -
     `docker compose logs api | grep task_assigned_email` - prints exactly one
     line; the same line parses through `python3 -m json.tool` as a single JSON
     object; and it carries `to`, `subject`, `body` and `task_id`, checked by
     membership rather than by eye. `grep -c` prints 1: one assignment, one
     invitation.
  8. The recipient's side. As the teammate, `GET /api/v1/tasks/assigned-to-me`
     returns the task, `GET /api/v1/task-lists` returns `[]`, and the list the
     task lives in answers **404**. D-01 and D-02 in the running container, not
     only in the test suite: the assignee can reach their work and cannot see
     the list it belongs to.
  9. The negative leg. The same call with no `Authorization` header is 401
     `application/problem+json` carrying the RFC 9110 challenge
     `WWW-Authenticate: Bearer` and the generic refusal - no hint that the
     route exists for somebody else. The transcript shows the field name
     lower-cased, `www-authenticate: Bearer`, because that is how uvicorn puts
     it on the wire; HTTP field names are case-insensitive, and the capture is
     left exactly as it was observed rather than tidied to match the spelling
     used in prose.
 10. The stack is left UP and HEALTHY (`docker compose ps` at the end),
     `/health` reports `"database":"ok"`, and `make test` passes **998 tests at
     100.00% coverage** against `taskmanager_test` - which the initdb script
     recreated along with the volume. A later plan's gate is therefore not the
     thing that discovers the volume was wiped.

On credentials, because this rehearsal necessarily has some:

  * The two passwords used below - `cold-start-rehearsal-2026` and
    `teammate-cold-start-2026` - were invented for this file and appear nowhere
    else in the repository. That is the whole of D-14: the project ships no
    known credential, and a password that had to be documented anywhere would
    be one. Both accounts exist only in a local volume that
    `docker compose down -v` discards.
  * The ONE redaction in this file is the two access tokens. Each was a live
    bearer credential for thirty minutes against this local stack, signed with
    the `.env` secret that is never committed, and a transcript in the
    repository is readable by anyone who can read the repository - the same
    argument docker/entrypoint.sh makes about a container log (T-3-31). Each is
    replaced by a marker, and the command immediately after each login records
    the length the redacted value had.
  * The `tee` and `sed` steps write to a scratch path outside the repository.
    That is deliberate (the 03-11 precedent): writing them inside `.planning/`
    would make the `git status --porcelain` at the end non-empty, and that is
    the one line in this transcript that has to be blank.

Nothing below is elided. Everything is verbatim, including the build output and
the timings - with one mechanical exception that is worth stating rather than
leaving for a reader to wonder about: the repository's `trailing-whitespace`
pre-commit hook trimmed the spaces `psql` and `docker compose` pad some of
their lines with. No character that carries information was touched, and the
two earlier captures in this project were committed through the same hook.

A REST API for task lists and the tasks inside them.

**There is no seeded account, so start by making one.**

1. `POST /api/v1/auth/register` with an email, a full name and a password.
2. Click **Authorize** at the top right of `/docs` and enter that same email
   (in the `username` field - OAuth2 fixes the name, this API's usernames are
   email addresses) and password.
3. Every other route is then callable, and each one acts as the account you
   registered.

Errors are RFC 9457 `application/problem+json` documents, from every route.
