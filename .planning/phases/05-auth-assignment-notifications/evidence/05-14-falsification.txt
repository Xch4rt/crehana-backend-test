Plan 05-14: the load-bearing assertions of tests/integration/api/test_assignment.py,
observed failing against a deliberately broken implementation.

Nothing in this plan is a TDD RED in the usual sense: plans 05-08 and 05-12 shipped
the use cases and the routes, so every test written here is green the moment it is
written. A green test over working code says nothing about whether the test could
ever have gone red, so the two assertions the threat register leans on were
falsified instead - each by breaking the one decision it exists to pin, running the
module, and reverting.

=== Falsification 3 (NOTF-03): the write made non-durable ===

Task 2's failure test claims that a re-read through the API is what proves the
requirement, and that asserting the 200 alone would pass against an
implementation which swallowed the notifier's exception *and* lost the write.
That claim is checked by removing `await self._uow.commit()` from
`AssignTask.execute`, which produces exactly such an implementation: the
response is still 200 carrying the new assignee, and the row never changed.

The 200 and the response body both passed; the re-read is the assertion that
failed, which is the whole reason it is there.
