What this proves: roadmap success criterion 1 - "the domain package imports no
third-party library" - is now enforced rather than asserted, and the gate that enforces
it is strictly stronger than the one that was already there. RUN 1 and RUN 2 are the
whole point of this plan: with `import greenlet` sitting inside taskmanager.domain, the
new AST test goes red while `lint-imports` exits 0 and reports "Domain is framework-free
KEPT". That is Conflict C-01 demonstrated instead of argued - a `forbidden` contract can
only prove the nine *enumerated* distributions are absent, and greenlet is the tenth.
RUN 3 and RUN 4 plant `import pydantic` instead and both gates fail, which shows the new
test subsumes the enumerated contract rather than replacing it. RUN 5 and RUN 6 are the
shipped tree, both green.

The violation module was deleted immediately after the red runs and exists neither on
disk nor in git history as a tracked file; `git status --porcelain` shows no _violation
entry. The green runs below are the shipped tree.

greenlet was chosen as the planted import on purpose. It is a real, already-installed
package (3.5.6, a transitive dependency of SQLAlchemy[asyncio]), so the demonstration
uses an import that would genuinely resolve at runtime - not a name invented to fail -
and it is absent from `.importlinter`'s forbidden_modules list, which is exactly the
blind spot being closed.

`--no-logo` replaces the [logo elided] marker Phase 1 used: the flag suppresses
import-linter's nine-line ASCII banner at the source, so every capture below is
verbatim, exit codes included, with nothing edited out.

This is the gap. A third-party import is sitting in taskmanager.domain and every
contract reports KEPT.

It is not that grimp failed to see the import - compare the file counts against RUN 6:
48 files / 79 dependencies clean, 50 / 80 here. The graph grew by two nodes (the
_violation module and greenlet itself, which was not previously in the graph at all) and
by one dependency. grimp resolved the import perfectly; the contract simply had nothing
to say about it, because `forbidden_modules` is a list of nine names and greenlet is not
one of them.

The wildcard escape hatch does not help either. `forbidden_modules = *` was executed
during this phase's research and reported `dataclasses`, `datetime` and `enum` as
violations, because a graph built with `include_external_packages = True` carries stdlib
modules as first-class nodes. There is no contract type meaning "everything except the
standard library", which is why the check had to be written as a test.

================================================================================
APPENDIX - the second failure mode: a scan that scans nothing
================================================================================

Everything above proves the new test catches a bad import. It does not prove the test is
looking at anything, and that is the quieter way for a check of this shape to die: if
`DOMAIN_ROOT` stops resolving - a renamed package, a moved src/ layout, one wrong
`parents[N]` - then `rglob("*.py")` yields nothing, the comprehension builds an empty
list, and `assert violations == []` passes forever. Green build, zero enforcement, and
nothing in the output to suggest anything is wrong. That is what
test_the_domain_package_is_actually_scanned exists for, so it was worth observing too.

With MINIMUM_DOMAIN_MODULES temporarily raised to 99 - standing in for a scan that finds
nothing, since both assertions in the guard fail the same way:

================================================================================
APPENDIX 2 - the same test on the target runtime
================================================================================

`sys.stdlib_module_names` is per-interpreter, and this project runs two: CPython 3.14.3
on the host and CPython 3.13 in Docker and CI. The sets are not identical - 297 names on
3.14.3, 290 on python:3.13-slim-trixie (verified by running
`python -c "import sys; print(len(sys.stdlib_module_names))"` in both) - so "passes on
the host" does not imply "passes in CI" for a check built on this constant.

$ .venv/bin/pytest -q                  # host, CPython 3.14.3
140 passed, coverage 100.00%
EXIT=0

$ make docker-test                     # python:3.13-slim-trixie, CPython 3.13.15
140 passed, coverage 100.00%
EXIT=0

Same test count, same result. Every module the domain actually imports - dataclasses,
datetime, typing, uuid, enum, collections.abc - is in both sets, so the seven-name
difference between the two interpreters never touches this test.
