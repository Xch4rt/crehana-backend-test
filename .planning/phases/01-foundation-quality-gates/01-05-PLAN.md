`PIP_NO_CACHE_DIR=1`, `PIP_DISABLE_PIP_VERSION_CHECK=1`. Use `WORKDIR /app`, create a
virtualenv at `/opt/venv` and prepend `/opt/venv/bin` to `PATH`. Then copy
`requirements.txt` and run `pip install -r requirements.txt` BEFORE copying any source, so
a code edit does not invalidate the dependency layer. Then copy `pyproject.toml` and `src`
and run `pip install --no-deps .` — that non-editable install is the only reason the
`[project]` packaging block in `pyproject.toml` is mandatory.

Stage `runtime` from the same pinned base. Set `PYTHONDONTWRITEBYTECODE=1`,
`PYTHONUNBUFFERED=1` and a `PATH` including `/opt/venv/bin`. Create the non-root account
with `useradd --system --create-home --shell /usr/sbin/nologin app` — not a `chmod 777` on
the app directory. Copy the venv with `COPY --from=builder /opt/venv /opt/venv`, set
`WORKDIR /app`, then `USER app`, `EXPOSE 8000`, and a `CMD` in exec form running
`uvicorn --factory taskmanager.main:create_app --host 0.0.0.0 --port 8000`. Copy no `src/`,
no `tests/` and no configuration files into this stage — the package already lives inside
the venv. Declare no `ENV` or `ARG` carrying a secret; secrets are injected at runtime by
compose in Phase 3.

Stage `test` from `builder`. Copy `requirements-dev.txt`, then run
`pip install -r requirements-dev.txt && pip install --no-deps -e .` — the editable
reinstall replaces the builder's non-editable copy so coverage paths stay
`src/taskmanager/...` and only one copy of the code sits on `sys.path`. Then copy
`pytest.ini`, `.flake8` and `.importlinter` into the workdir and copy `tests` to
`./tests`. Create the same `app` user, `chown -R app:app /app /opt/venv`, switch to
`USER app`, and set `CMD ["pytest"]`.

Note what the `test` stage deliberately does NOT do: it never installs or runs
`pre-commit`. The image has no `.venv`, and plan 04's `repo: local` hooks use
`.venv/bin/`-qualified entries, so a `pre-commit run` inside the container could only fail.
The container's gate is `pytest`, which already carries the coverage threshold and the
architecture contract test.

Then verify by building and running. `docker build --target runtime -t taskmanager .`;
`docker run --rm taskmanager whoami` must print `app`; `docker run --rm taskmanager python
--version` must report Python 3.13.x; `docker run --rm taskmanager ls -a /app` must show
no `.env`; `docker history taskmanager` must contain no secret; the image must be well
under 500 MB (research measured 285 MB). Then `docker build --target test -t
taskmanager-test .` and `docker run --rm taskmanager-test` — the full suite including the
coverage gate must pass inside the container on Python 3.13, which is the authoritative
interpreter for this project.

Create `.github/workflows/ci.yml` with `name: CI`, triggered on both `push` and
`pull_request` with no branch filter, and a single job `quality-gates` on
`runs-on: ubuntu-latest`.

Give the job a `services.postgres` entry using the pinned image `postgres:18-alpine`
(never `postgres:latest`), with `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` set
to non-secret CI-only values, port 5432 mapped, and `options` carrying
`--health-cmd "pg_isready -h 127.0.0.1 -U <user> -d <db>"` plus `--health-interval 5s`,
`--health-timeout 5s`, `--health-retries 10`, `--health-start-period 10s`. The
`-h 127.0.0.1` is load-bearing: the official image's init-time server listens only on a
Unix socket, so a health command without it passes too early. Do not hand-roll an
`until pg_isready` bash loop — the runner blocks on the declared health check before the
first step runs. This service is unused by Phase 1 tests on purpose: having it green now
means Phase 3's integration tests add a pytest marker rather than new CI infrastructure.

Set job-level `env` with `DATABASE_URL` (a `postgresql+psycopg://` URL matching the
service credentials against `localhost:5432`) and `JWT_SECRET` set to an obviously fake
CI-only value of at least 16 characters. These are the two settings fields with no
default; without them the workflow could not even import the app. Never reference a real
credential or a repository secret here — nothing in Phase 1 needs one.

Steps, in order:
1. `actions/checkout@v7`
2. `actions/setup-python@v7` with `python-version: '3.13'`, `cache: pip`, and a multi-line
   `cache-dependency-path` listing `requirements.txt` and `requirements-dev.txt`
3. `Install dependencies`: upgrade pip, `pip install -r requirements-dev.txt`, then
   `pip install -e .` (editable, for the same reason as everywhere else)
4. `Format check (black)`: `black --check src tests`
5. `Import order check (isort)`: `isort --check-only src tests`
6. `Lint (flake8)`: `flake8 src tests`
7. `Type check (mypy strict)`: `mypy src tests`
8. `Architecture contracts (import-linter)`: `lint-imports` — its own named step so a
   boundary failure is a readable red step in the job log in addition to being a failing
   test inside pytest. Never `python -m importlinter.cli`.
9. `Tests with coverage gate`: `pytest` (the gate rides along via `pytest.ini` addopts)

Every gate above is a direct tool invocation, and that is a requirement, not a style
preference. This workflow must NEVER invoke `pre-commit` in any form — not `pre-commit run`,
not `pre-commit run --all-files`, not the `pre-commit/action` action. Plan 04's `repo: local`
hooks use `.venv/bin/`-qualified entries so they resolve on a developer host that has no
activated virtualenv; a GitHub runner installs dependencies into the system Python and has
no `.venv` at all, so any `pre-commit` step could only fail with "command not found". The
nine steps above are the CI-side equivalent of the same gate set, running the same tools at
the same pinned versions from `requirements-dev.txt`. Keep the step names aligned with the
hook ids so a reader comparing `ci.yml` against `.pre-commit-config.yaml` can see the
correspondence; plan 06 records the split as an ADR.

Pin every action to its major tag as written above. Do not add a `permissions` block
granting write scopes — this job needs none; if a `permissions` block is added at all it
must be `contents: read`.

Then validate locally: parse the YAML and assert the job exists, the service image is
`postgres:18-alpine`, the step list contains a black, isort, flake8, mypy, lint-imports and
pytest command, and that the string `pre-commit` appears in no step `run` and no step
`uses`. This workflow has never executed on a real runner (RESEARCH assumption A2) — plan
08's checkpoint is the first real run; budget one fix-up commit there.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Build context -> image layers | Anything not excluded by `.dockerignore` is permanently readable in a published layer |
| Container process -> host kernel | A root container process narrows the blast radius of any later RCE to nothing |
| GitHub Actions runner -> repository | A workflow with write permissions or a compromised action can rewrite history |
| Docker Hub / GitHub -> build | Base images and actions are third-party code executed on every build |
| Developer-host gate config -> venv-less environments | A config that assumes `.venv` exists silently breaks wherever it does not |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-23 | Elevation of Privilege | container runtime user | mitigate | `useradd --system --create-home --shell /usr/sbin/nologin app` plus `USER app` in the final stage; asserted by `docker run --rm taskmanager whoami` returning `app` |
| T-01-24 | Information Disclosure | `.env`, `.git`, `.planning` baked into a layer | mitigate | `.dockerignore` from plan 01 excludes all three; asserted by `docker run --rm taskmanager ls -a /app` and `docker history` containing no `secret` match |
