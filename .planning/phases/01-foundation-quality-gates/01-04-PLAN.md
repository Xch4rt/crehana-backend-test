   `detect-private-key` and `check-added-large-files` are the supply-chain/secret controls
   for threat T-01-18.
2. `https://github.com/PyCQA/isort` at `rev: 9.0.1`, hook id `isort`. It picks up
   `profile = "black"` from `pyproject.toml`; do not repeat the profile as a hook arg.
3. `https://github.com/psf/black-pre-commit-mirror` at `rev: 26.5.1`, hook id `black`.
   Use the mirror repo, not `psf/black` itself.
4. `https://github.com/PyCQA/flake8` at `rev: 7.3.0`, hook id `flake8`, with
   `additional_dependencies` pinning `flake8-bugbear==26.9.9`,
   `flake8-comprehensions==3.17.0` and `pep8-naming==0.15.1` to the same versions as
   `requirements-dev.txt`. A flake8 hook without its plugins silently stops running the
   B/C4/N checks.

Then a fifth `repo: local` entry with two hooks. Both `entry` values MUST be
venv-qualified relative paths, never bare tool names:
- id `mypy`, name `mypy (strict)`, `entry: .venv/bin/mypy`, `language: system`,
  `types: [python]`, `pass_filenames: false`, `args: [src, tests]`
- id `import-linter`, name `import-linter contracts`, `entry: .venv/bin/lint-imports`,
  `language: system`, `pass_filenames: false`, `always_run: true`

Why the `.venv/bin/` prefix is load-bearing: pre-commit never activates a virtualenv, and
this host has no project tools on `PATH` outside `.venv` — which is exactly why every other
command in this phase is `.venv/bin/`-qualified. A bare `entry: mypy` therefore dies with
`command not found` whenever the hook runs from a shell that has not sourced
`.venv/bin/activate`, and that includes `.venv/bin/pre-commit run --all-files` itself as
well as a real `git commit`. The relative paths resolve because the repository root is
pre-commit's working directory for every hook, regardless of where git was invoked from.
RESEARCH's example shows these two hooks with bare `entry: mypy` / `entry: lint-imports`;
that recipe was reasoned, not executed (RESEARCH Assumption A1) and does not hold on this
host — deviate from it deliberately and say so in the SUMMARY.

These two are deliberately NOT mirror repos. Both are whole-program tools: mypy needs the
real environment because `plugins = ["pydantic.mypy"]` aborts with exit 2 in an isolated
env with no pydantic, and `import pytest` in `tests/` would be unresolvable there;
`lint-imports` needs the installed `taskmanager` package to resolve `root_package`. Using
`language: system` also guarantees the hook, `make typecheck` and `make arch` execute the
same command with the same versions, with no `additional_dependencies` list to drift from
`requirements-dev.txt` (RESEARCH Pitfall 6). `entry: .venv/bin/lint-imports`, never
`python -m importlinter.cli`.

Carry one consequence forward deliberately: a `.venv/bin/`-qualified entry means
`.pre-commit-config.yaml` only works where `.venv` exists — the developer host. CI runners
and the Docker image have no `.venv`, so neither may ever invoke `pre-commit run`. CI runs
black, isort, flake8, mypy, `lint-imports` and pytest as its own named steps instead (plan
05 asserts that `pre-commit` appears nowhere in `ci.yml`), and plan 06 records this choice
and its consequence as an ADR.

After writing the file, run `.venv/bin/pre-commit install`, then
`.venv/bin/pre-commit run --all-files` twice. The first run may rewrite files (that is
what formatters do); the second run must report every hook `Passed` with zero file
modifications. If the second run still modifies files, the hook order is wrong — fix the
order rather than adding exclusions.

Then prove the local hooks actually execute with NO activated virtualenv and a minimal
`PATH` — the failure mode this configuration exists to prevent, and a recipe research never
ran. Run
`env -i HOME="$HOME" PATH="/usr/bin:/bin:/usr/local/bin" .venv/bin/pre-commit run --all-files`.
Keep git reachable on that `PATH` (`/usr/bin/git` on macOS) and keep `HOME` so pre-commit
finds its hook cache. If any hook reports `command not found` or `Executable ... not found`,
the entry is not venv-qualified — fix the entry, never relax the check.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Working tree -> commit | pre-commit is the last automated checkpoint before code becomes history |
| pre-commit hook env -> repository tools | An isolated hook env that lacks the project's dependencies silently degrades the gate it claims to run |
| Invoking shell -> hook executable resolution | A hook entry that depends on the caller's `PATH` runs a different tool, or none, depending on who committed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-17 | Tampering | pre-commit hook repositories | mitigate | Every `rev` is an exact pinned tag verified against the GitHub tags API during research; no `HEAD`, no floating branch |
| T-01-18 | Information Disclosure | a private key or oversized blob committed | mitigate | `detect-private-key` and `check-added-large-files` hooks from `pre-commit-hooks v6.0.0` |
| T-01-19 | Repudiation | a mypy hook that reports green from an isolated env missing pydantic | mitigate | `repo: local` + `language: system` so the hook runs the same mypy as `make typecheck`, with the pydantic plugin present (RESEARCH Pitfall 6) |
| T-01-20 | Repudiation | an architecture hook invoking the always-exit-0 `python -m` form | mitigate | Hook `entry` is the `lint-imports` console script at `.venv/bin/lint-imports`; grep asserts `importlinter.cli` appears nowhere in either file |
| T-01-21 | Tampering | `make lint` rewriting files and masking a violation | mitigate | `lint` uses `--check` / `--check-only` only; rewriting lives exclusively in `format` |
| T-01-22 | Denial of Service (developer) | hook oscillation blocking every commit | mitigate | Hook order isort -> black -> flake8 -> mypy -> lint-imports, verified by two consecutive `--all-files` runs with `git diff --quiet` |
| T-01-45 | Repudiation | a local hook whose bare `entry` resolves to nothing outside an activated venv, so the gate is skipped or errors out non-deterministically | mitigate | Both `repo: local` entries are `.venv/bin/`-qualified relative paths; asserted by a YAML check and by a full `pre-commit run --all-files` under `env -i` with a minimal `PATH` |
</threat_model>
