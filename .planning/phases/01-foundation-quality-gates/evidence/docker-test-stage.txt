Evidence: the Docker `test` stage was observed failing before it was shipped green
Plan 01-05, Task 1 — captured 2026-09-18 on darwin/arm64, Docker Engine 29.2.0

WHY THIS FILE EXISTS
--------------------
The research document publishes a three-stage Dockerfile and states it was built and
run. Copied verbatim, its `test` stage does NOT pass this repository's suite: the stage
copies `pytest.ini`, `.flake8`, `.importlinter` and `tests/`, but plan 01-02 added a unit
test that reads `.env.example` from the repository root to assert that the file documents
every declared settings field and nothing else. The research Dockerfile predates that test.

This is exactly the failure shape this phase exists to eliminate: a container gate that
looks complete, builds successfully, and reports "coverage gate reached" while one test
is red. `docker run` exits non-zero, so `make docker-test` would have failed for an
evaluator on the first try.

Note the two lines above the summary: coverage was 100% and the threshold message
printed anyway. A reader skimming the tail of this log would conclude the gate passed.


THE FIX
-------
One token added to the `test` stage's configuration COPY:

    COPY pytest.ini .flake8 .importlinter .env.example ./

`.env.example` is a tracked placeholder file containing no credential. The real `.env`
stays excluded from the build context by `.dockerignore`, and neither file exists in the
`runtime` stage, which copies only `/opt/venv`.

$ docker history taskmanager | grep -ci secret

368 MB, not the 285 MB the research measured. The difference is the platform: this build
is linux/arm64 with a BuildKit attestation manifest attached, and `docker image ls`
reports the uncompressed size of the multi-manifest entry. Well under the 500 MB ceiling
either way; the number is recorded rather than the research figure repeated.

The runtime CMD was also exercised end to end, because "the image builds" and "the image
serves" are different claims:
