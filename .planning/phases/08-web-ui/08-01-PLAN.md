<objective>
Make the frontend exist, make it gated, and make `docker compose up` serve it — without the backend
learning that it has a browser client. This plan builds the scaffold, the one fetch boundary every
screen will use, the login/register screen, the two-stage UI image with its nginx reverse proxy, the
compose service, the five `make` targets, the CI job, the pre-commit hook, the pytest gate over the
pins, and the four ADRs that record the decisions.

Purpose: UI-01 (register / log in / log out), UI-05 (refusals rendered from the RFC 9457 body),
UI-06 (one command, same-origin proxy, no CORS), UI-07 (TypeScript strict, eslint, vitest behind
`make` targets and a CI Node job). Roadmap Phase 8 SC-1, SC-3, SC-4.

Output: a `frontend/` package that lints, type-checks and tests clean; a `ui` compose service on
`http://localhost:8080` proxying `/api/` to `api:8000`; ADR-105 through ADR-108, with the README's
quoted ADR count moved to 108 in the same commit as the appends.

Response shapes, exactly:

- `UserResponse` = `{id, email, full_name, created_at}`
- `UserSummaryResponse` = `{id, full_name, email}` — note: no `created_at`
- `TaskListResponse` = `{id, owner_id, name, description, created_at, updated_at, total_tasks,
  completed_tasks, completion_percentage}`
- `TaskResponse` = `{id, task_list_id, title, description, status, priority, created_at,
  updated_at, due_date, completed_at, assignee_id}`
- `TaskCollectionResponse` = `{items: TaskResponse[], total_tasks, completed_tasks,
  completion_percentage}` — the three counters describe the **whole list**, never the filtered
  `items` (ADR-009). Never recompute them from `items`.
- `TaskStatus` = `"pending" | "in_progress" | "completed"`
- `TaskPriority` = `"low" | "medium" | "high"`; `TaskCreateRequest.priority` defaults to `"medium"`
- Allowed status moves (`ALLOWED_TRANSITIONS`, ADR-097): `pending -> in_progress | completed`;
  `in_progress -> pending | completed`; `completed -> in_progress` **only**. A request for the
  status the task already has is a 200 no-op, not an error.

The error body, on **every** refusal, media type `application/problem+json`:
`{type: "urn:taskmanager:problem:<code>", title, status, detail, instance, code, errors?}`.
`errors` appears only when non-empty. The `code` values that exist today: `validation_error`,
`business_rule_violation`, `invalid_status_transition`, `not_found`, `task_not_found`,
`task_list_not_found`, `user_not_found`, `conflict`, `duplicate_task_list_name`,
`email_already_registered`, `authentication_failed`, `authorization_failed`, `domain_error`.

**The Dockerfile trap (ADR-102).** The `test` stage receives only what it explicitly `COPY`s. A
test that reads a repository-root file is green on the host and a **collection error** in
`make docker-test` and in CI until the `COPY` line exists. Task 4 adds a gate that reads three files
under `frontend/`, so the `COPY` line and the gate land in the same commit and that commit's
verification is `make docker-test`, not `make test`.

**The rehearsal (`scripts/clean-clone-rehearsal.sh`, ADR-103).** It stops the developer's stack,
clones the committed tree, builds `--no-cache`, and executes the shell lines between README.md's
`rehearsal:begin` / `rehearsal:end` markers. It rewrites one line: a bare `make up` becomes a
backgrounded invocation plus `rehearsal_wait_for_a_healthy_api` and
`rehearsal_assert_the_api_is_ours`, the second of which asserts that the container publishing
`:8000` is this rehearsal's own `api`. Task 3 adds the same pair for the `ui` service on `:8080`.
`tests/unit/test_clean_clone_rehearsal.py` drives the script against a **planted** README in
`tmp_path` and never runs Docker, so it is unaffected by changes to the generated preamble - re-run
it anyway.
