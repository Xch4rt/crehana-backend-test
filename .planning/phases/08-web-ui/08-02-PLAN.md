**The three facts this plan exists to get right.**

1. **The completion percentage describes the list, never the filtered view (ADR-009, D-11).**
   `GET /api/v1/task-lists/{list_id}/tasks?status=&priority=` answers
   `{items, total_tasks, completed_tasks, completion_percentage}` where the three counters are
   computed over the **whole list** by one SQL aggregate, regardless of the filter. The UI renders
   those three numbers as given. Recomputing a percentage from `items.length` is the single most
   likely way to ship a UI that contradicts the API it sits on, and it is the one behaviour this
   project has an ADR about. `README.md`'s quickstart step 6 is exactly this case: one item comes
   back, and the counters still say `total_tasks: 2`, `completed_tasks: 1`,
   `completion_percentage: 50.0`.

2. **The allowed status moves (`ALLOWED_TRANSITIONS`, ADR-097).**

   | From | To |
   |------|----|
   | `pending` | `in_progress`, `completed` |
   | `in_progress` | `pending`, `completed` |
   | `completed` | `in_progress` **only** |

   `completed -> pending` is the single forbidden move and answers **409**
   `invalid_status_transition`, whose `errors` member carries `{"from": ..., "to": ...}`. A request
   for the status a task already has is a **200 no-op**, not an error.

3. **Status is changed only through the dedicated endpoint.**
   `PATCH /api/v1/task-lists/{list_id}/tasks/{task_id}/status` with `{status}`. The general
   `PATCH .../tasks/{task_id}` accepts `title`, `description`, `priority` and `due_date` and
   **does not accept `status`** — sending it there is a 422. An empty patch body is also a 422.

**Response shapes** (repeated from 08-01 so this plan is self-contained; `types.ts` is their typed
form):

- `TaskListResponse` = `{id, owner_id, name, description, created_at, updated_at, total_tasks,
  completed_tasks, completion_percentage}`
- `TaskResponse` = `{id, task_list_id, title, description, status, priority, created_at,
  updated_at, due_date, completed_at, assignee_id}`
- `TaskCollectionResponse` = `{items: TaskResponse[], total_tasks, completed_tasks,
  completion_percentage}`
- `UserSummaryResponse` = `{id, full_name, email}`
- `TaskStatus` = `"pending" | "in_progress" | "completed"`;
  `TaskPriority` = `"low" | "medium" | "high"`
- The problem body, on every refusal:
  `{type, title, status, detail, instance, code, errors?}`

**Operations this plan drives**, all already exported by `client.ts`:
`listTaskLists`, `createTaskList`, `updateTaskList`, `deleteTaskList`, `listTasks`, `createTask`,
`updateTask`, `deleteTask`, `changeTaskStatus`, `listUsers`, `assignTask`, `unassignTask`,
`listAssignedTasks`.

Two shapes to get right because they differ from their neighbours:
`deleteTaskList` and `deleteTask` answer **204 with no body**; `unassignTask` answers
**200 with the updated `TaskResponse`**, not 204.

**Navigation: a hand-rolled view switch, not a router (D-05, ADR-106).** `App` holds
`view: {name: "lists"} | {name: "tasks"; list: TaskListResponse} | {name: "assigned"}` in state.
There is no `react-router`, no URL synchronisation, no deep link and no browser Back between
screens; that cost is deliberate and plan 08-03 names it in the README's Pending list. Do not add a
routing dependency — the pins are gated by `tests/architecture/test_frontend_gates.py` and a new
dependency would need an ADR this plan does not own.

**No pagination anywhere, because the API has none (API-01).** Every list route returns everything
it has in a fixed total order. Do not invent a page control.

**Constraints inherited from 08-01, all of them gates:**
- `localStorage` and `document.cookie` are eslint errors under `src/**` (D-06).
- TypeScript `strict`; no `any`, no `as` cast written to silence the compiler.
- Every dependency is exact-pinned; adding one fails `make test` unless the lockfile and the pins
  gate agree, and it would need an ADR.
- Tests import `describe` / `it` / `expect` from `vitest` (no globals) and find controls by
  **accessible name** — label text, button text, `role` — never by a test id.

## Trust Boundaries

| Boundary | Description |
