<objective>
Close the one gap `06-VERIFICATION.md` left open: roadmap SC-3 ("every test asserts on response
bodies, and every mutating test re-reads through the API") is false for
`tests/integration/api/test_permission_matrix.py`, and the gate that exists to make that a build
failure cannot see it.

Two halves, both real:

1. **The gate is blind.** `MUTATING_VERBS` is `{post, put, patch, delete}` matched against the
   *attribute name*, so `client.request(cell.row.method, ...)` — the only way the matrix issues a
   request — is recorded as the verb `"request"`, which is in `REQUEST_VERBS` (so the test counts
   as an HTTP test) and in nothing half (b) looks at. Every POST/PATCH/PUT/DELETE in a 76-cell
   table is invisible to the re-read check, and the gate reports zero offenders (WR-02).
2. **The test is thin where it succeeds.** For the 2xx mutating cells (rows 2, 6, 9, 10, 11, 14,
   15, 16, 17, 18) the `else` branch of `assert_the_body_the_status_promises` calls only
   `assert_no_challenge_was_issued` — no `WWW-Authenticate`, not `problem+json`. A DELETE that
   answered 204 and deleted nothing passes. The refusal cells (401/403/404) are fully
   body-asserted already; only success is thin.

Purpose: TEST-05 / roadmap SC-3, and plan 06-02's own must-have truth, which this module
contradicts today.

**The choice this plan makes, and why.** Both halves are fixed by assertions, not by an exemption.
The body-assertion half has no exemption mechanism at all — half (a) of the gate is deliberately
escape-hatch-free (D-07), and SC-3's wording has no opt-out — so that half was never optional. For
the re-read half, `no_reread` was available and is *not* taken: the matrix is parametrized over a
table, so a re-read keyed on the row is one field on `Row` plus one block in the test, and it turns
ten rows of "the handler said 201" into ten rows of "the row is in the database". An exemption
would have bought three lines and left the destructive rows — `DELETE` a list, `DELETE` a task,
unassign — proving only that nothing complained. The module docstring's claim that per-route
persistence is proved next door stays true and is not the point: the gate's rule is per test, and
this test mutates.

**WR-03 is deliberately not fixed here** (gap scope item 3). Its cheapest sub-case — "a re-read
whose result is discarded still satisfies half (b)" — is not a few lines: requiring the GET's
response to reach an `assert` means binding the call's target name, accepting the inline
`(await client.get(...)).json()` form only inside an `assert`, and re-auditing every re-read the
06-02 sweep added for false positives. That is a gate-redesign task, it is recorded in
`06-REVIEW.md` as a latent weakness with no live exploit, and the verifier confirmed no test in
today's suite uses the shape. Out of scope, on purpose. Also out of scope: WR-05, WR-06, WR-07,
WR-08, WR-10, WR-11 and every IN-*.
