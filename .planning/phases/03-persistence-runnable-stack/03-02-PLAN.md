<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host/CI environment → Alembic | `DATABASE_URL` carries credentials into the migration process |
| Docker host → db container | Published port 5432 exposes PostgreSQL on the host loopback |
| repository → container filesystem | The initdb script is executed by the database superuser on first boot |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-05 | Information disclosure | `alembic.ini` | mitigate | No `sqlalchemy.url` key exists, so a live credential is never written into a config file that Alembic may print; the URL arrives via `config.attributes` or `DATABASE_URL` (RESEARCH Pitfall 3) |
| T-3-06 | Tampering / data loss | `downgrade()` | mitigate | `downgrade` is exercised only against `taskmanager_test`; the container entrypoint added in plan 03-10 runs `alembic upgrade head` and never `downgrade`, and this plan's verify commands name `taskmanager_test` explicitly |
| T-3-07 | Information disclosure | published port 5432 | accept | D-15 requires it so host-side `make test` reaches the same container; credentials are the obviously-fake `taskmanager/taskmanager` pair, identical to CI's, and the ADR in plan 03-11 records the trade honestly |
| T-3-08 | Tampering | `docker/initdb/*.sql` | mitigate | The init script is mounted read-only (`:ro`), contains one guarded `CREATE DATABASE` and no `GRANT`, and runs only on an empty data directory |
| T-3-09 | Spoofing | `db` healthcheck | mitigate | `pg_isready -h 127.0.0.1` forces a TCP probe, so `depends_on: service_healthy` cannot be satisfied by the init-time Unix-socket-only server (D-07) |
| T-3-SC | Tampering | pip installs | accept | No package is installed; `alembic` 1.20.0 was already pinned and audited in RESEARCH §"Package Legitimacy Audit" (`3 OK / 0 SUS / 0 SLOP`) |
</threat_model>
