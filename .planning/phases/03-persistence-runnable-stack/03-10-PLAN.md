<objective>
Turn the repository into the one-command stack the brief asks for: `docker compose up` starts
PostgreSQL and the API, the API waits for a genuinely ready database, applies the migrations, and
reports healthy only once `GET /health` answers 200.

Three of RESEARCH's seven verified traps live in this plan: `psycopg.connect()` rejects the
project's own `DATABASE_URL` (Pitfall 2), the current Dockerfile copies neither `alembic.ini` nor
`migrations/` nor `docker/` into any stage (Pitfall 5), and the runtime stage sets `USER app`
before any new `COPY` would land.

Purpose: this is the evaluator's first five minutes — `cp .env.example .env`, `docker compose up`,
`http://localhost:8000/health`, `make docker-test`.

the final `Makefile` targets.

  <action>
    Create `docker/entrypoint.sh` following RESEARCH Pattern 7, as POSIX `sh` with `set -eu`.
    Three steps, each with a comment:
      1. A bounded readiness probe: a `python - <<'PY' ... PY` heredoc that reads
         `os.environ["DATABASE_URL"]` and, for up to 30 attempts one second apart, opens
         `sqlalchemy.create_engine(url, pool_pre_ping=True).connect()` and executes
         `text("SELECT 1")`. It must go through SQLAlchemy, not `psycopg.connect()` — state the
         Pitfall 2 reason in the comment: libpq understands `postgresql://`, not SQLAlchemy's
         `+psycopg` driver token, so `psycopg.connect(DATABASE_URL)` fails permanently on the
         first attempt and the retry loop then burns all thirty on a healthy database. On success
         `sys.exit(0)`; after exhausting the attempts print a clear message to stderr and
         `sys.exit(1)`. The per-attempt log line must print the exception class name only and
         never the URL, so a credential cannot reach a container log.
      2. `alembic upgrade head`.
      3. `exec uvicorn --factory taskmanager.main:create_app --host 0.0.0.0 --port 8000` — `exec`
         so uvicorn becomes PID 1 and receives signals.
    Add a header comment recording the decision from RESEARCH Open Question 1: the retry logic
    lives here rather than in a module under `src/taskmanager/` because coverage is measured over
    that package with no `omit` and no `pragma: no cover` allowed (CLAUDE.md), and the behaviour is
    proven end to end by the cold-start rehearsal in Task 3 — a stronger proof than a unit test of
    a `range(30)` loop.

    Extend the Dockerfile `runtime` stage with the lines Pitfall 5 identified, placed after
    `WORKDIR /app` and using `--chown=app:app` so they land correctly despite `USER app` at L59:
    `COPY --chown=app:app alembic.ini ./`, `COPY --chown=app:app migrations ./migrations`,
    `COPY --chown=app:app docker/entrypoint.sh ./docker/entrypoint.sh`, then
    `RUN chmod +x ./docker/entrypoint.sh` (set the bit in the build rather than relying on the host
    file mode surviving the build context on every platform), then
    `ENTRYPOINT ["./docker/entrypoint.sh"]`. Keep the existing `EXPOSE 8000`, keep `CMD` (now the
    default argument list behind the entrypoint), and keep `USER app` — the image must still run
    as non-root.

    Add the `HEALTHCHECK` from RESEARCH Pattern 8 with
    `--interval=10s --timeout=5s --start-period=30s --retries=3` and a Python one-liner using
    `urllib.request` that exits 0 only on status 200, wrapped in an explicit `try/except` so a 503
    becomes exit 1 rather than relying on a traceback's exit code (RESEARCH assumption A3). Comment
    the `--start-period=30s`: the API is not listening until the migrations finish, and without it
    the container flaps to `unhealthy` before it ever had a chance.

    Extend the Dockerfile `test` stage with `COPY alembic.ini ./` and `COPY migrations ./migrations`
    so the `migrated_database` fixture can find them. The test stage must **not** receive the
    entrypoint: D-06 says the pytest fixture owns the test schema, and the stage's `CMD ["pytest"]`
    stays exactly as it is.

    Add a comment in the Dockerfile recording that the runtime stage intentionally gains only these
    three files and no application source — the package still arrives exclusively through
    `/opt/venv`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host → container | The image runs application code with whatever privileges the Dockerfile grants it |
| `.env` on the host → container environment | Every credential the stack uses crosses here |
| container logs → developer / CI output | The entrypoint runs before any application logging policy applies |
| Docker network → published ports | `8000` and `5432` are exposed on the host loopback |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-30 | Elevation of privilege | runtime image user | mitigate | `USER app` is preserved and every new `COPY` uses `--chown=app:app`; an acceptance criterion asserts `id -u` is non-zero and that the copied files are owned by `app`, so the Pitfall 5 fix cannot silently reintroduce root |
| T-3-31 | Information disclosure | entrypoint retry log | mitigate | The per-attempt line prints only the exception class name; the URL is never echoed, and an acceptance criterion checks no print statement carries it |
| T-3-11 | Information disclosure | `.env` | mitigate | `.env` stays git-ignored and `.dockerignore`d; compose reads it at run time through `env_file` and it is never baked into a layer |
| T-3-32 | Tampering / data loss | entrypoint migrations | mitigate | The entrypoint runs `alembic upgrade head` only — never `downgrade` — so a container restart can never destroy data; the migration step runs before uvicorn, which the log-ordering check proves |
| T-3-33 | Spoofing | container healthcheck | mitigate | The healthcheck exits 0 only on HTTP 200 from `/health`, and `/health` answers 200 only when the database probe succeeded; the stop-the-database check proves an unhealthy database really produces an unhealthy container |
| T-3-07 | Information disclosure | published ports 8000 and 5432 | accept | D-15 requires both for the documented evaluator flow and for host-side `make test`; credentials are the obviously-fake `taskmanager/taskmanager` pair and the ADR in plan 03-11 records the trade |
| T-3-34 | Denial of service | startup race on migrations | mitigate | D-06 keeps migrations in the entrypoint rather than the FastAPI lifespan, and `depends_on: condition: service_healthy` plus the bounded retry loop mean the container fails loudly instead of looping forever |
| T-3-SC | Tampering | image build | accept | No package is installed beyond the already-pinned `requirements*.txt`; base images stay pinned to `python:3.13-slim-trixie` and `postgres:18-alpine`, never `:latest` |
</threat_model>
