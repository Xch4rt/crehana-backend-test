<objective>
Build the integration-test harness this phase turns on, and use it immediately to prove the
schema.

The harness is where four locked decisions become mechanical: D-01 (per-test isolation by
transaction rollback with an explicit `create_savepoint` join mode), D-02 (the real migration
builds the test schema), D-03 (one fast, instructive failure when PostgreSQL is unreachable) and
D-04 (the test database is `taskmanager_test`, derived or overridden).

Then three test modules prove what `alembic check` cannot: that the CHECK constraints of DB-04
actually refuse bad values, that DB-05's cascade actually deletes tasks, and that timestamps
really come back timezone-aware.

Purpose: from this plan onward `make test` requires a reachable PostgreSQL. That is deliberate
(D-03) and the failure message is part of the deliverable.
Output: `tests/integration/{__init__,conftest,test_migrations,test_schema,test_constraints}.py`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test process → PostgreSQL | Test SQL is authored in-repo but must still model the injection surface the repositories will have |
| failure messages → developer terminal / CI log | A connection failure is the most likely place a live DSN leaks into a public CI log |
| test transaction → durable storage | The isolation contract is what stops a test from leaving state behind |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-10 | Information disclosure | `_require_database` fail-fast message | mitigate | The message renders the URL with `make_url(url).render_as_string()`, whose default masks the password; an acceptance criterion greps the output of a run with the password `secret` and requires zero matches |
| T-3-17 | Tampering | test SQL | mitigate | Every statement is `text()` with bound parameters; an acceptance criterion greps for f-string SQL and requires zero matches — the same discipline the Phase 4 filter endpoints will need |
| T-3-18 | Tampering / data loss | `command.downgrade` inside the suite | mitigate | The downgrade test runs inside a transaction that is rolled back, targets `taskmanager_test` only, and an acceptance criterion re-counts the three tables afterwards |
| T-3-19 | Denial of service | residue between test runs | mitigate | D-01 rollback isolation, verified by running `make test` twice and by asserting `SELECT count(*) FROM users` is 0 after the suite |
| T-3-02 | Tampering | `ck_tasks_status` / `ck_tasks_priority` | mitigate | Proven enforced by insert-and-refuse tests, which is the only proof available since `alembic check` is blind to CHECK constraints (Pitfall 8) |
| T-3-03 | Tampering | cascade rules | mitigate | `test_deleting_a_task_list_cascades_to_its_tasks` and its two siblings prove no orphan or dangling row can survive a delete (DB-05) |
| T-3-SC | Tampering | pip installs | accept | No package is installed |
</threat_model>
