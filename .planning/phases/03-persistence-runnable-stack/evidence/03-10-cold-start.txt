Plan 03-10 Task 3 - the cold-start rehearsal
============================================

Captured 2026-09-19 on macOS 15 / Docker Desktop, linux/arm64, against the
committed docker-compose.yml with no override file of any kind.

What this transcript proves, in order:

  1. The volume is discarded first (`down -v`). /docker-entrypoint-initdb.d only
     runs on an empty data directory (03-RESEARCH.md Pitfall 7), so a warm-volume
     run would prove nothing about the evaluator's first command.
  2. `docker compose up --build -d` starts db and api - and NOT test, which
     carries a profile.
  3. `api` reaches `healthy`, which under D-09 means the image's own HEALTHCHECK
     got HTTP 200 from /health, which under D-08 means the database probe passed.
  4. In `docker compose logs api`, the Alembic revision line appears BEFORE the
     first uvicorn line. That is D-06's ordering, read off the log rather than
     assumed: the entrypoint waited, migrated, and only then exec'd the server.
  5. /health answers 200 with "database":"ok" on the published host port.
  6. `docker compose run --rm --build test` - the body of `make docker-test` -
     runs the whole suite, integration tests included, and meets the coverage
     gate. No `--profile` flag: `run` enables the profiles of the service it
     names.
  7. `docker compose exec api id -u` prints a non-zero uid: the three new COPY
     lines did not reintroduce root (T-3-30).
  8. Falsification. With the database stopped, the container turns `unhealthy`
     and /health answers 503 with the same body shape. Starting the database
     returns it to `healthy`. This is what distinguishes a healthcheck wired to
     the database probe from one that only proves the process is alive (T-3-33).

The stack was left RUNNING at the end of this capture (db + api, api healthy).
`make down` stops it; `docker compose down -v` also discards the volume.
