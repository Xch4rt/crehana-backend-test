<objective>
Implement the first two of the three repository adapters — task lists and users — against the
Protocols Phase 2 declared, and prove the three properties that make them honest adapters rather
than a thin wrapper: they return domain entities that survive the session closing, they flush so
D-13's error translation has a constraint name to key on, and they never commit.

The `.commit()` gate lands here too, as an architecture test in the style of
`tests/architecture/test_domain_is_stdlib_only.py`, because roadmap SC-4 requires the property to
be *provable*, not merely reviewed.

Purpose: these two adapters are the pattern the task adapter (plan 03-07) repeats, and the
`SqlAlchemyUnitOfWork` (plan 03-08) constructs all three.
Output: `infrastructure/db/repositories/{task_lists,users}.py`, their two integration suites, and
the SC-4 gate.
</objective>

```python
class TaskListRepository(Protocol):
    async def get(self, task_list_id: UUID) -> TaskList | None: ...
    async def add(self, task_list: TaskList) -> None: ...
    async def update(self, task_list: TaskList) -> None: ...
    async def delete(self, task_list_id: UUID) -> None: ...
    async def list_for_owner(self, owner_id: UUID) -> Sequence[TaskList]: ...
    async def exists_with_name(self, owner_id: UUID, name: str) -> bool: ...


class UserRepository(Protocol):
    async def get(self, user_id: UUID) -> User | None: ...
    async def get_by_email(self, email: str) -> User | None: ...
    async def add(self, user: User) -> None: ...
    async def list_all(self) -> Sequence[User]: ...
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository → PostgreSQL | Entity values become bound parameters; this is the SQL-injection surface Phase 4's filters will widen |
| database rejection → HTTP response | A constraint violation must become a typed business error, never a driver message the client can read |
| adapter → application layer | The port types are the only vocabulary allowed to cross |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-17 | Tampering | repository queries | mitigate | Every query is built with `select()` / `delete()` and bound parameters; an acceptance criterion asserts `session.query` and f-string SQL are absent |
| T-3-13 | Information disclosure | conflict errors | mitigate | `test_the_conflict_error_does_not_echo_the_address` asserts the raised `EmailAlreadyRegisteredError` carries neither the address nor the constraint name, so registration cannot become an account-enumeration oracle |
| T-3-14 | Information disclosure | unmapped `IntegrityError` | mitigate | `test_an_unrecognised_integrity_error_is_re_raised` proves the bare `raise` path, which Phase 2's catch-all turns into the fixed 500 body with no message |
| T-3-20 | Elevation of privilege | `list_for_owner` / `exists_with_name` | mitigate | Both queries are owner-scoped in SQL rather than filtered in Python, so a Phase 4 use case cannot accidentally perform an unscoped read (ASVS V4, ADR-008) |
| T-3-21 | Repudiation / integrity | uncommitted writes | mitigate | The SC-4 gate makes it impossible for an adapter to make a write durable outside the use case's explicit `commit()`, so no write exists that the transaction log cannot explain |
| T-3-SC | Tampering | pip installs | accept | No package is installed |
</threat_model>
