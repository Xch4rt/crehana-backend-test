Make the running stack usable the moment it starts: seed the demo user the actor seam points at,
and rehearse the cold start that proves it.

Purpose: D-01 gives every request a fixed actor id, and `task_lists.owner_id` is a foreign key. On
a fresh volume that user does not exist, so an evaluator's very first
`POST /api/v1/task-lists` after `docker compose up` would fail on a foreign-key violation. The
whole point of the seam is that the mandatory use case works with zero setup.
Output: the seed step in `docker/entrypoint.sh`, the idempotence proof, and the cold-start
transcript.

```sh
    """
    INSERT INTO users (id, email, password_hash, created_at, updated_at)

    ON CONFLICT DO NOTHING
    """

engine = create_engine(os.environ["DATABASE_URL"])

    connection.execute(SEED, {...})
engine.dispose()
PY
```

  <action>
    Add a step `2b` to `docker/entrypoint.sh`, between `alembic upgrade head` and `exec uvicorn`,
    as its own `# --- 2b. ...` comment banner matching the existing ones, containing the heredoc
    given in `<interfaces>`. Fill the parameters with `DEMO_USER_ID`, the email
    `demo@taskmanager.local`, a `password_hash` placeholder, and `datetime.now(UTC)` for both
    timestamps.

    Four things the comment banner must say, because each is a decision a reader could otherwise
    undo:
      - **Why here and not in a migration.** A data row is not a schema change; an Alembic data
        migration would make the demo user part of the schema's history and Phase 5 could not remove
        it by deleting a file. Placement after `upgrade head` is required because the table has to
        exist.
      - **Why a heredoc and not a module under `src/taskmanager/`.** A module there would owe a unit
        test under the no-`omit`/no-`pragma` coverage rule, and it would add a node to the import
        graph that has to import `presentation`. ADR-037 already won this argument for the readiness
        probe — reference it rather than restating it.
      - **Why `ON CONFLICT DO NOTHING` with no conflict target.** Three executions against the live
        database produced rowcounts 1, 0 and 0: a second run with the same id is absorbed by the
        primary key, and a run with a different id and the same email is absorbed by
        `uq_users_email_lower`. A targeted `ON CONFLICT (id) DO NOTHING` would not absorb the second
        of those, and under `set -eu` the container would abort — so the untargeted form is what
        makes a restart safe, not a shortcut.
      - **Why the placeholder hash is not a credential.** The value stored is not a valid Argon2
        encoded hash, so `pwdlib`'s verification can never succeed against it; this identity cannot
        become a live account, and Phase 5 deletes the row together with the seam. Do not write a
        plausible-looking hash.

    Import `DEMO_USER_ID` rather than pasting the UUID: the constant must exist exactly once (D-03),
    and importing from `presentation` is legal for a `main`-level consumer. The heredoc is not a
    module under `src/`, so it adds no node to import-linter's graph and cannot break a contract —
    confirm that by running `make arch` rather than assuming it.

    Then prove the idempotence rather than claiming it. With the compose database running, execute
    the seed body three times — once fresh, once with the same id, and once with a different id but
    the same email — printing `result.rowcount` each time, and capture the transcript verbatim to
    `.planning/phases/04-task-lists-tasks/evidence/04-11-seed-idempotence.txt`, headed with the
    commands and the date. Clean up the third row afterwards if it was inserted (it must not have
    been) and leave the test database as it was found.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| container startup → database state | The entrypoint writes a row; anything it writes exists in every deployment of this image |
| seeded identity → the authorization model | A row that every unauthenticated request acts as is, by definition, privileged |
| container logs → operator | A log line is readable by anyone who can run `docker compose logs` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-4-64 | Elevation of privilege | the demo row becoming a live account in Phase 5 | mitigate | `password_hash` is a deliberately unverifiable placeholder that Argon2 can never match; the comment says so, plan 04-12 records it as an ADR, and Phase 5 deletes the row together with the seam |
| T-4-65 | Spoofing | the demo seam read as authentication by a reviewer | mitigate | `actor.py`'s docstring says "not authentication" in those words and a test asserts the phrase is present; the entrypoint comment repeats that this step disappears in Phase 5 |
| T-4-66 | Denial of service | a restart aborting the container on a conflict | mitigate | `ON CONFLICT DO NOTHING` with **no** target absorbs both the primary-key and the `uq_users_email_lower` collision; three executed rowcounts are captured as evidence, and the restart leg of the rehearsal observes it in the real container under `set -eu` |
| T-4-67 | Information disclosure | credentials in a startup log line | mitigate | The seed prints nothing on success, following the step-1 probe's rule that a successful step produces no output; the connection string is never echoed (T-3-31) |
| T-4-68 | Tampering | a second copy of the demo UUID drifting from `actor.py` | mitigate | The entrypoint imports `DEMO_USER_ID`; `grep -c` for the literal in `entrypoint.sh` printing `0` is an acceptance criterion |
| T-4-69 | Repudiation | a cold-start claim that was never run | mitigate | The rehearsal transcript is captured verbatim, including retries and timings, and the `201` it records is impossible without the seed |
| T-4-SC | Tampering | npm/pip/cargo installs | accept | This plan installs no package; the image's dependency set is unchanged |
</threat_model>
