Plan 04-11 Task 2 - the cold-start rehearsal on an empty volume
===============================================================

Captured 2026-09-19 on macOS 15 / Docker Desktop, linux/arm64, against the
committed docker-compose.yml, Dockerfile and Makefile with no override file of
any kind and no edit to any of the three (the last command in this transcript
checks that).

This extends evidence/03-10-cold-start.txt rather than replacing it. Phase 3's
rehearsal could show that a fresh stack reaches `api healthy`, that the Alembic
revision runs before uvicorn, and that /health is wired to the database - but it
could not show the API doing anything, because Phase 3 shipped no route. This one
can: it walks the brief's mandatory use case (create a list, create a task, move
it to `completed`, read the statistics back) on a stack that was an empty volume
ninety seconds earlier.

What this transcript proves, in order:

  1. `docker compose down -v` discards the volume first. Without `-v` the database
     is already migrated AND already seeded, so the run would prove nothing about
     the evaluator's first command - which is the only run that matters here.
  2. `docker compose up -d --build` starts db and api, and NOT test, which carries
     a profile (03-10's finding, re-observed).
  3. `api` reaches `healthy` 6 seconds after `up` returns - three polls, 2s apart.
  4. The log shows the entrypoint's order (D-06): the Alembic revision line, then
     the uvicorn lines. The seed step sits between them and prints nothing, which
     is the intended behaviour - like the readiness probe, a successful step is
     silent (T-4-67: a container log is readable by anyone who can run
     `docker compose logs`, so the seed never echoes what it wrote).
  5. `POST /api/v1/task-lists` answers **201** with a `Location` header. This is
     the line the whole plan exists for: `task_lists.owner_id` is a foreign key to
     `users.id`, so without the seed step this request is a foreign-key violation
     and the D-01/D-02 arrangement is broken on the evaluator's very first call.
     The `owner_id` in the body reads `00000000-0000-4000-8000-00000000de00` -
     `DEMO_USER_ID` from actor.py, the row the entrypoint wrote.
  6. The mandatory use case end to end: the task is created `pending`/`medium`,
     moved `pending -> in_progress -> completed`, and the envelope statistics go
     from (1, 0, 0.0) to (1, 1, **100.0**). The collection endpoint's per-list
     statistics move with them.
  7. `docker compose restart api` returns to `healthy` in 7 seconds, and this is
     Task 1's idempotence claim observed in the real container under `set -eu`
     rather than in a script: the seed ran a second time against a database that
     already holds the row. `docker compose logs api | grep -c -E
     'IntegrityError|Traceback'` prints **0**, the data survives the restart, and
     `SELECT ... FROM users` at the end returns exactly **one** row.
  8. `/health` still answers 200 with `"database":"ok"` - the Phase 3 contract is
     intact.

One thing worth reading carefully in step 7's log: the second boot prints the two
Alembic context lines but NO `Running upgrade` line. The migration was already at
head, so it did nothing - which is what `upgrade head` on a restart is supposed to
look like, and the same shape the seed step takes one line further down (it too
ran, and it too changed nothing).

Nothing diverged from the plan. No retry line appeared in either boot: the
compose healthcheck on `db` plus `depends_on: condition: service_healthy` meant
the database was already accepting connections when the entrypoint's probe first
asked, so the probe was silent both times. The bounded retry loop is still load-
bearing under a plain `docker run`, where nothing waits - that is 03-10's
falsification, not re-run here.

The stack was left RUNNING at the end of this capture (db + api, both healthy).
`make down` stops it; `docker compose down -v` also discards the volume.

The only elision below is the body of the image build - ~230 lines of pip
download progress from a cold BuildKit cache, which say nothing about this plan.
It is marked where it was cut; everything else is verbatim, including the
timings.
